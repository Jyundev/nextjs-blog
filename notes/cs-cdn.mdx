작업 중에 CDN URL과 Object Storage URL이 코드베이스에 섞여 있는 걸 발견했다.

둘 다 이미지 같은 파일을 URL로 제공하는데, 뭐가 다른 건지 명확하게 구분이 안 됐다.

## Object Storage

파일 자체를 저장하는 곳이다.

이미지, 영상, 문서 같은 걸 객체(Object) 단위로 저장하고, URL로 접근한다. 대표적으로 Amazon S3.

쉽게 말하면 **원본 파일이 실제로 올라가 있는 창고**다.

## CDN

Object Storage에 있는 파일을 전 세계에 **복제**해서, 사용자와 가까운 서버에서 빠르게 내려주는 네트워크다.

한국 사용자가 미국 S3 버킷에 있는 이미지를 요청하면 느리다. CDN을 붙이면 한국 서버에 캐시된 걸 바로 받아온다.

즉, **창고는 S3, 배달망은 CDN**.

## 그래서 뭘 써야 하나

Object Storage 단독으로도 URL 접근은 된다. 근데 CDN 없이 쓰면:

- 원본 서버에 요청이 몰린다
- 지역별 속도 차이가 크다
- 비용도 더 든다 (S3 egress 비용)

실서비스라면 보통 **S3(또는 GCS) + CloudFront(또는 Cloudflare)** 조합으로 쓴다.

---

## 우리 팀 기준

엄밀한 정의는 아니지만, 실무에서 빠르게 구분할 때 이렇게 판단하기로 했다.

> **사용자가 URL로 직접 접근했을 때 권한 없이 볼 수 있으면 CDN, 아니면 Object Storage**

공개 정적 파일은 CDN, 접근 제어가 필요한 원본 파일은 Object Storage 쪽으로 분류한다.

---

## 실제 작업 내용

기존 코드에서 CDN / Object Storage가 명확한 기준 없이 혼재되어 있었다.

게다가 당시 CDN과 Object Storage는 다른 팀이 관리하는 서버였다. 우리 팀이 직접 제어할 수 없는 구조라 파일이 어디서 오는 건지, 캐시가 되는 건지 아닌 건지 파악이 안 되는 상태.

일단 지금 상황에서는 외부 CDN보다 구조를 단순하게 정리하는 게 먼저라고 판단해서, WAS 하위 디렉토리 기반으로 바꾸는 중이다.

- 정적 리소스: `/static`
- 업로드 파일: `/files`

나중에 트래픽이 늘면 그때 CDN 붙이는 게 맞는 순서인 것 같다.
